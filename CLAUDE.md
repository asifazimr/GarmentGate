# GarmentGate

## Product

GarmentGate is a managed B2B marketplace that connects garment buyers worldwide with garment manufacturers. **GarmentGate is the contracting party in the middle**: buyers contract with us, and we contract with manufacturers. Every quote, chat message, order, file and payment goes through the platform.

### Roles

| Role           | Who                             | Can                                                                                                                                                       |
| -------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BUYER`        | Brands, retailers, importers    | Browse anonymized manufacturer profiles, request quotes (RFQs), chat via the platform, place and track orders, pay GarmentGate                            |
| `MANUFACTURER` | Factories and production houses | Maintain their profile and capabilities, respond to RFQs, chat via the platform, fulfil orders, receive payouts from GarmentGate                          |
| `ADMIN`        | GarmentGate staff               | Verify manufacturers, moderate content, manage quotes/orders/disputes, see real identities on both sides, configure margins and payouts                   |
| `INSPECTOR`    | GarmentGate QC inspectors       | See the inspections assigned to them (with the factory's address), upload photos and file AQL reports. Created by admins only                             |
| `PARTNER`      | Freight forwarders and carriers | See only GarmentGate's bookings with their company (`/partner`), accept legs, post tracking updates and references, upload papers. Created by admins only |

A user has exactly one role. Authorization is enforced in the API (guards on every route); the web app hides UI by role but is never the security boundary.

## Core rule: no direct contact

Buyers and manufacturers must **never** be able to identify or contact each other directly. Any change that could leak identity or contact details is a bug, whatever the feature.

1. **Anonymized manufacturers.** Buyers only ever see a manufacturer's public code, e.g. `MFR-BD-0421` (`MFR-<ISO country code>-<4-digit number>`). Company name, legal entity, address, website, people's names, emails, phone numbers, social handles, and certificate numbers that identify the factory are never sent to a buyer.
   - Buyer-facing API responses are built from dedicated "public" serializers/DTOs. Never return a Prisma model directly, and never rely on the frontend to hide fields.
   - Uploaded media (photos, tech packs, certificates) shown to buyers must be reviewed or processed to remove logos, signage and EXIF/metadata.
   - Buyers are shown to manufacturers in the same anonymized way (e.g. `BYR-<country>-<number>`) unless an admin explicitly decides otherwise.
2. **Contact filtering on all user-generated content.** Chat messages, RFQ descriptions, quote notes, profile text, reviews, file names, and any other free text pass through the shared contact filter in the API before they are stored or delivered. It detects and redacts emails, phone numbers, URLs/domains, messaging handles (WhatsApp, WeChat, Skype, Telegram, Instagram, etc.), and common obfuscations (`name [at] gmail dot com`, spelled-out digits, spaced numbers).
   - Filtering happens server-side. Client-side checks are only a UX hint.
   - Keep the original text in an admin-only field and flag the message for moderation; deliver the redacted version.
   - Repeated attempts are tracked per user so admins can act.
3. **Money and contracts flow through GarmentGate.** Buyers pay GarmentGate; GarmentGate pays manufacturers. No feature may expose bank details, invoices or documents of one side to the other.

When adding any endpoint, socket event, email, notification, export, or search index field, ask: _could this reveal who the other side is or how to reach them?_

### How the rule is enforced in code

- **Buyer-facing data goes through `apps/api/src/modules/catalog/public.serializer.ts` only** (`toPublicManufacturer`, `toPublicProduct`). They copy an explicit allowlist, re-filter free text and scrub the company's own names, website and owners' names (`scrubText`), then parse with **strict** schemas (`PublicManufacturerSchema`, `PublicProductSchema` in `packages/shared`) that throw on any extra key. Load data with the selects in `catalog.queries.ts`. To expose a new field to buyers, add it to the strict schema and the serializer, and extend `public.serializer.spec.ts` (sentinel tests assert nothing identifying leaks).
- **Margin stays hidden both ways.** Buyers only get `buyerUnitPriceMinor`; manufacturers only get `manufacturerUnitPriceMinor` (their queries don't even select buyer prices). Catalog buyer prices come from `pickCatalogRule` + `applyMarkup` in `modules/pricing/margin.ts`.
- **Images**: uploads land privately under `originals/`; the BullMQ `media` worker (`modules/media`) decodes with Sharp, bakes in orientation, **drops all metadata** (EXIF/GPS/XMP/IPTC/ICC) and writes WebP renditions (320/800/1600) under `renditions/`. Browsers only ever get signed URLs to renditions. Factory photos and product images also need **admin approval** (`/admin/media/*`) before buyers see them (logos, signage, faces).
- Factories can check all of this themselves: **Factory profile → Buyer preview** renders `/manufacturer/profile/preview`, which uses the same serializer as buyers.
- **RFQs and quotes** (`modules/rfq`): buyers publish RFQs (`POST /rfqs`); `matchRfq` (`rfq-matching.ts`) reaches listed factories by category (incl. parent/child), MOQ ≤ quantity and monthly capacity over the production window; catalog requests (with a `productId`) are invite-only. Factories see RFQs through `ManufacturerRfqsService` only: the buyer is a `BYR-` code, title/description are contact-filtered and scrubbed of the buyer's names, and buyer/target prices are never selected. Submitting a quote prices it immediately with `pickQuoteRule` (buyer-specific rule > category > parent > default) + `applyMarkup` and offers it to the buyer; the offered price is stored, so later rule changes don't touch it (admins can override with `PATCH /admin/quotes/:id/price`). Buyers see `BuyerQuoteSchema` (strict) with badges from `quoteBadges` in `packages/shared`. Accepting (`POST /rfqs/:code/quotes/:id/accept`) awards the RFQ, declines the other quotes and creates a `DRAFT` order, guarded by conditional updates so it can only happen once.
- **Documents**: PDFs go through the same `media` worker as images: `sanitizePdf` (`modules/media/document-processor.ts`, pdf-lib) drops document info, XMP, annotations, embedded files, scripts and form fields, then garbage-collects unreachable objects, and writes `sanitized/<fileId>.pdf`. RFQ files reach factories only when sanitized **and** approved in `/admin/moderation`, under a neutral name (`RFQ-2026-00043-tech-pack-1.pdf`).
- **Orders** (`modules/orders`): the state machine lives in `packages/shared/src/order/order-state.ts` (`ORDER_TRANSITIONS`: who may move an order where; `nextStep` drives the highlighted next action). Every status change goes through `OrdersService.move`: state-machine check, conditional update (two clicks can't both win), an `OrderEvent`, notifications by code. SAMPLING / SAMPLE_APPROVED are only reached through the sample endpoints; deposit received (→ IN_PRODUCTION) and QC results are staff-only; disputes need a reason and resume only where they were (or close). Views per audience (`order-views.ts`): `BuyerOrderSchema` / `ManufacturerOrderSchema` are strict, the factory sees the buyer's text scrubbed and only approved buyer photos, the buyer only approved factory media.
- **Purchase orders**: `GET /orders/:code/purchase-order` renders (pdf-lib, `purchase-order.ts`) the caller's own PO: buyer ↔ GarmentGate at the buyer price, or GarmentGate ↔ factory at the factory price with no buyer identity (ship-to is country/port only). Staff pick `?side=`. GarmentGate's details come from `PLATFORM_*` env vars.
- **Order media**: buyer sample photos and factory production photos/videos go through the media worker (videos: `video-processor.ts` blanks metadata boxes and zeroes GPS/telemetry track samples without re-encoding) and admin review (`sample-photos`, `milestone-media` in `/admin/moderation`) before the other side sees them.
- **QC** (`modules/qc`): buyers (or staff) book an inline (`DURING_PRODUCTION`) or final random (`PRE_SHIPMENT`) inspection; entering QC opens a final one anyway (one open inspection per order and type, partial unique index). Staff create inspectors (`POST /admin/inspectors`, they set a password from the reset email) and assign them (`PATCH /admin/inspections/:id`). Inspectors use `/inspector/inspections/*` and only see their own jobs. Reports follow ISO 2859-1 level II (`aqlVerdict` in `packages/shared/src/qc/aql.ts`): the inspector can fail a lot that passes on counts, never pass one that fails. A final PASS advances QC → READY_TO_SHIP (balance due); a FAIL lets the **buyer** send the order back for rework (QC → IN_PRODUCTION only after a failed final) or dispute. Inspector photos go through the media worker and admin review (`inspection-photos`); the PDF report is staff and factory only. Summaries are scrubbed of each side's names. **The global `RolesGuard` keeps inspectors off every route that doesn't name them** (`@Roles(... 'INSPECTOR')` or `@AnyRole()` for session/notification routes).
- **Gig QC inspectors** (`qc/gig.service.ts`, `gig.controller.ts`, shared `qc/gig.ts`; pages `/inspectors/apply`, `/inspector/tasks`, `/inspector/earnings`, staff tabs under `/admin/inspectors`): freelancers apply publicly (`POST /inspectors/apply`, throttled, duplicates dedupe silently); staff approve only certified applicants (`/admin/gig/applications/:id/review`), which creates an `INSPECTOR` user (password from the reset email) with an `InspectorProfile` (home coordinates, service radius, types). Their task feed (`GET /inspector/tasks`) lists unassigned inspections of located factories within the radius (country fallback without coordinates), skipping factories they inspected `rotationLimit` times in 90 days; claiming is one conditional update and snapshots the day rate (`inspections.payUsdMinor`). Staff locate factories (`PUT /admin/manufacturers/:code/location`); for a located factory the report needs a GPS check-in within `checkInRadiusM` (`POST /inspector/inspections/:id/check-in`, shown on the job page). Filing the report earns the pay (revenue → `INSPECTOR_PAYABLE`, key `gig-earned:<id>`) and picks `auditSampleBps` of reports for a re-inspection (staff notified). Staff rate each report once (`POST /admin/inspections/:id/rate`, stars on the order's inspection panel; `rating` is staff-only in `OrderInspectionSchema`); a low average after `minRatingsForSuspension` ratings suspends the inspector (no tasks, no claims). Payout details (bank, bKash, Nagad) reset to unverified on any change; staff verify, then record the weekly transfer (`/admin/gig/inspectors/:userId/pay`: an OUTBOUND payment per inspection, `INSPECTOR_PAYABLE` → cash, key `gig-paid:<id>`). Settings: `platform_settings.gig` (`/admin/gig/settings`; defaults USD 80/day, 500 m, 2 per 90 days, 10% audits, suspend below 3 after 5). Gig inspectors are still `INSPECTOR`s: the `RolesGuard` and `/inspector/*` ownership checks apply unchanged. Tests: `gig.e2e-spec.ts`, `gig.test.ts`.
- **Factory plans** (`modules/plans`, shared `plans/plans.ts`; pages `/manufacturer/plan`, `/admin/plans`): Free / Pro / Premium. Terms live in `platform_settings.factory_plans` (`PUT /admin/plans/settings`; defaults Free USD 0 · 10 listed products; Pro USD 99/mo or 990/yr · 50 · boost 1 · 100 bps off the markup; Premium USD 249/mo or 2,490/yr · unlimited · boost 2 · 200 bps · RFQ head start; head start 24 h). The tier in force is `manufacturer_profiles.planTier` (+ `searchBoost` for the index), recomputed by `PlansService.applyTier` from the live `PlanSubscription` (`grantedTier`: ACTIVE or PAST_DUE with 7 days' grace). **Subscription engine** (`subscriptions.service.ts`, shared by factory plans and buyer Plus): one `plan_subscriptions` table, exactly one owner (factory profile or buyer company, DB check: factories PRO/PREMIUM, buyers PLUS), one live per owner (partial unique indexes); features register `onChange(kind, …)` to recompute perks. **Card plans**: checkout creates a Stripe Checkout Session (mode subscription, inline `price_data` in USD, `subscriptionId` in metadata); the shared webhook fans events out through `StripeEvents` (payments → `SubscriptionsService.stripeEvent`): `customer.subscription.*` set status/period (a new live plan cancels the previous one; a cancelled row never revives), `invoice.paid` books cash → revenue once (`SUBSCRIPTION` ledger kind, key `sub-invoice:<id>`) and a `PlanInvoice` (counted as cash in by the reconciliation); factories cancel at period end (`POST /manufacturer/plan/cancel`). **Staff grants** (`PUT /admin/manufacturers/:code/plan`, `GrantPlanSchema`: tier, last day, optional amount + transfer reference booked as revenue, note; FREE ends one) are refused while a card plan is live. **Perks**: listed (PUBLISHED / PENDING_REVIEW) products capped by `assertCanList` (drafts free, nothing unlisted on downgrade); `applyMarkup(price, rule, markupDiscountBps)` on catalog prices (repriced on a tier change) and quotes, never below the rule's per-unit floor; Meilisearch ranking rule `searchBoost:desc` after `sort`; open RFQs reach factories without a head start at `headStartEnds` (≤ half the quote window): their invitation gets a later `visibleAt`, `ManufacturerRfqsService.access` hides it until then, and the BullMQ `factory-plans` sweep (5 min; not scheduled in tests, call `PlansService.sweep`) announces it once (`notifiedAt`, claimed in one UPDATE) and ends lapsed grants. Tests: `plans.e2e-spec.ts`, `plans.test.ts`.
- **GarmentGate Plus** (`plans/buyer-plus.service.ts`, shared `plans/buyer-plus.ts`; pages `/buyer/plus`, Admin → Factory plans → Buyer Plus): a buyer membership on the same engine (`GET /buyer/plus`, `POST /buyer/plus/checkout {interval}`, `POST /buyer/plus/cancel`; staff `PUT /admin/buyers/:code/plus` with `GrantPlusSchema`, refused over a live card plan). In force = `buyer_profiles.plusActive`. Every term is staff-set in `platform_settings.buyer_plus` (`PUT /admin/plus/settings`; defaults USD 49/mo or 490/yr, free inspections, 50% off samples, priority RFQs, merchandiser). Perks: `chargeInspection` waives members' inspection fees and `chargeSample` applies `discountedFee` (both via `plusPerks` in `payments/charges.ts`, at charge time only); members' RFQs carry `priority: true` in `ManufacturerRfqSummarySchema` and are listed first (factories never learn who); joining asks staff to assign a merchandiser when none is set. Tests: `plus.e2e-spec.ts`.
- **Texts (SMS / WhatsApp)** (`modules/messaging`, shared `messaging/messaging.ts`; settings card on every role's settings page, staff `/admin/messaging`): people verify a mobile number (`POST /me/messaging/phone` texts a 6-digit code, `@PhoneCodeThrottle`, hashed, 10 min, 5 tries; `POST /me/messaging/phone/verify`; `PUT /me/messaging/channel` SMS/WHATSAPP; `DELETE /me/messaging/phone`), stored as `users.phoneE164` and never sent to anyone but them and staff. Each notification category has a `text` preference (defaults on for quotes, orders, QC, payments, disputes). The `Notifier` queues a BullMQ `texts` job for each person with a verified number who wants it, when the type is in `platform_settings.messaging.types` and SMS or WhatsApp is on; `MessagingService.deliver` applies the daily cap (`dailyLimitPerUser`), sends WhatsApp only with an approved template for that type (`whatsappTemplates`, Twilio Content SID; variables {{1}} title, {{2}} body, {{3}} link) and otherwise SMS (`textBody`: the in-app wording plus the link, ≤ 300 chars), and logs every text in `outbound_messages` (`SKIPPED` with the reason; the verification code is never logged). The provider (`TEXT_PROVIDER`) is Twilio's REST API when `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` (+ `TWILIO_MESSAGING_SERVICE_SID` or `TWILIO_SMS_FROM`, optional `TWILIO_WHATSAPP_FROM`) are set, otherwise the API console. Delivery receipts arrive at `POST /messaging/twilio/status` (`TWILIO_STATUS_CALLBACK_URL`), checked with `twilioSignatureValid` and exempt from the origin check; statuses never move backwards. Staff: settings, the message log (CSV) and `POST /admin/messaging/test`. Tests: `messaging.e2e-spec.ts` (fake provider), `messaging.test.ts`.
- **Payments** (`modules/payments`): providers implement `PaymentProvider` (`manual`: bank transfer / LC confirmed by staff with an uploaded proof; `stripe`: PaymentIntents + signed webhook at `/payments/stripe/webhook`, enabled only when `STRIPE_*` env vars are set). Money moves only through `LedgerService.post`: balanced (checked in code and by the deferred DB trigger), append-only, one currency per transaction (DB trigger), idempotent by key, storing `unitsPerUsd` and the USD value. Accounts: PLATFORM_CASH, BUYER_ESCROW (per buyer), MANUFACTURER_PAYABLE (per factory), PLATFORM_REVENUE. Buyer deposit/balance → escrow; on confirmation the release schedule (`platform_settings.release_schedule`, default 25% PRODUCTION_START / 70% SHIPPED / 5% CLAIM_WINDOW holdback; staff edit it under Payments → Settings) is snapshotted into `order_releases` (tranches from `releaseTranches`, commission allocated first so it's never negative); staff approve each DUE tranche (escrow → payable + escrow → revenue, under a row lock on the order, DUE → RELEASED conditionally), then record the payout (optionally in another currency at the stored rate). The DELIVERED tranche is released automatically when the buyer confirms delivery (if escrow holds it). Refunds only from unreleased escrow. Buyer and factory views (`BuyerPaymentsSchema`, `ManufacturerPayoutsSchema`) are strict and never carry the margin; `/admin/finance/*` does. Factories can't ship until the balance is paid. **Channels**: every buyer charge (deposit, balance, shipping, fees, booking deposits) is paid into GarmentGate by card through Stripe (`PaymentChooser` + Stripe Payment Element, settled by the signed webhook; offered when `STRIPE_*` is set) or by bank wire / LC confirmed by staff; factories are never paid by buyers. **Payouts** go by bank transfer (SWIFT/local) from GarmentGate's account to the factory's **verified** `FactoryBankAccount` (`PUT /manufacturer/bank-account`, masked back to the factory; staff verify against the KYC'd legal name at `/admin/finance/bank-accounts/:id/review`; any change replaces the account and needs verifying again; one live account per factory, partial unique index). `payout` refuses without one and records `payments.factoryBankAccountId`; the finance inbox's `toPay` rows carry the bank details, so the staff table's CSV is the payout batch. Each release records the factory it's owed to (`order_releases.manufacturerProfileId`): after a factory replacement the old factory is paid from its own payable. Stripe Connect can't pay factories in BD/IN/VN/PK/TR/CN (US/UK/EEA/CA/CH recipients only), and Bangladesh isn't a Stripe account country, so GarmentGate's Stripe account sits with a company in a supported country; Stripe Global Payouts can plug in as a payout provider once Stripe confirms the recipient countries. **Service fees** (`payments/charges.ts`, `platform_settings.service_fees`, `PUT /admin/finance/fees`; defaults USD 200 per inspection day, USD 75 per sample, 14-day claim window): `chargeSample` / `chargeInspection` record an `OrderCharge` inside the transaction that creates the sample or inspection (requesting a sample; booking an inspection; QC opening the final one), in the order's currency at the reference rate; the buyer's first inspection ever is `waived`. The buyer pays `POST /orders/:code/fees/payments` (`SAMPLE_FEE` / `INSPECTION_FEE` payments into escrow, moved to revenue as they settle) and sees them in `BuyerPaymentsSchema.fees`; a departure waits for fees due. When the bulk deposit completes, paid sample fees are credited once (`orders.sampleCreditMinor`: revenue → escrow, and the balance due drops by it). The `CLAIM_WINDOW` tranche becomes DUE (`releaseClaimWindows`, run before the finance inbox and order finance) once delivery is older than the claim window with no open dispute; `DisputesService.open` refuses a DELIVERED order past the window. Release-mechanics tests (payments, qc-shipping) pin the classic 30/50/20 schedule; `fees.e2e-spec.ts` covers fees, the credit, the holdback and the window.
- **Chat** (`modules/chat`) is **relayed**: every thread is one company ↔ GarmentGate, tied to an RFQ or an order (unique per side, enforced by partial unique indexes); the DB trigger still refuses any participant from another company. Staff relay messages between the buyer's and the factory's threads (`POST /admin/messages/:id/relay`), labelled with the source's code and scrubbed of its names. Messages and file names are filtered on send (`originalContent` is staff-only); PDF attachments are also sanitized by the media worker and their text layer checked by the `chat-scan` worker (no OCR). Every contact-filter hit is audited as `moderation.contact_filtered`; 3 hits in 30 days raise a `WARNING`, 6 a `FINAL_WARNING` (`AccountWarning`). Flagged messages wait in `/admin/moderation` (release = false positive, delivers the original).
- **Realtime**: Socket.io gateway at `/socket.io` (no trailing slash), reached by browsers through the web app at `/api/socket.io`. The handshake authenticates with the `gg_at` cookie and checks the origin against `CORS_ORIGINS`; sockets drop when the token expires and the client refreshes and reconnects. Messages are sent over HTTP and pushed per audience (company rooms vs `admins`), typing indicators per open thread. The global JWT/roles/throttle guards apply to HTTP only. Events fan out through Redis (`@socket.io/redis-adapter` in `chat-io.adapter.ts`), so several API instances work; HTTP long-polling (the fallback behind Vercel's rewrite, `tryAllTransports`) needs sticky sessions on multi-instance deployments.
- **Contact filter** (`packages/shared/src/moderation/contact-filter.ts`, tests next to it): emails and "name at gmail dot com" forms, URLs/domains incl. `[.]`/"dot", messenger names (misspelt, spaced out, CJK) and handles, phone numbers in digits, other scripts, words (EN/BN/HI), letter lookalikes and spaced runs, with exclusions for dates, quantities, ranges, HS codes, sizes and platform codes. Masks with `[contact info hidden]`. Add a test for every new bypass.
- **Capacity booking** (`modules/capacity-booking`, shared `capacity/*`): factories describe **production lines** in SAM minutes per working day with a CM rate (`cmRateMinorPer100Min`), separate from the pieces-per-month capacity RFQ matching uses. They open **windows** (`capacity_slots`) sized by `slotCapacityMinutes`; overlapping open windows on a line are refused under a row lock on the line and by the `capacity_slots_no_overlap` exclusion constraint, and `bookedMinutes <= totalMinutes` is a check constraint (windows never shrink, close or delete below what's booked). **Supplier claims** (brand names + evidence) are staff and factory only: buyers get `brandBadges` (region, tier, count) on the public profile. Workforce and floor area reach buyers only as ranges (`WORKFORCE_BANDS`, `FLOOR_AREA_BANDS`). **Bookings** (`bookings.service.ts`, rules in shared `capacity/booking.ts`): buyers search open windows (`GET /capacity/search`, strict `CapacitySearchResponseSchema`: numbered lines and the marked-up rate from `bookingPrice`, never line codes/names or the CM rate) and place a **hold** (`POST /capacity/bookings`): minutes are reserved at once by one conditional `UPDATE … bookedMinutes + m <= totalMinutes` (`allocation.ts`), recorded per window in `capacity_booking_allocations` and released the same way. HELD → CONFIRMED needs the factory's accept **and** the deposit in escrow; price, deposit %, cancellation tiers and factory share are snapshotted on the booking (defaults at `/admin/capacity-booking/settings`, `platform_settings.capacity_booking`). Deposits are `Payment` rows with `capacityBookingId` (DB check: an order or a booking), confirmed by the usual staff / Stripe flow; `PaymentsService.onBookingDepositSettled` hands back to the booking. A BullMQ `capacity-booking` sweep (every minute; not scheduled in tests, call `BookingsService.sweep`) sends reminders and expires holds with a full refund, as do factory declines; a buyer cancelling a confirmed booking gets `cancellationSplit` (refund, factory share to its payable, the rest to revenue), all from escrow through the ledger. Conversion: CMT creates a DRAFT order at booked rate × SAM; full package opens an invite-only RFQ (`rfqs.capacityBookingId`) whose accepted quote's order is linked by the sweep. Unused minutes go back to the line, the deposit is carried into the order (two postings; the payment gets the `orderId`) and the booking follows its order through `OrderHooks`. **Partnerships** reserve every month (6–12) from open windows in one transaction, as PARTNERSHIP bookings whose deposit is due two weeks before each month.
- **Logistics** (`modules/logistics`, shared `logistics/*`): **the only way an order ships.** Shipments factories booked themselves before logistics were converted by the migration `retire_factory_shipments` into **historical** logistics shipments (`historical`: one main leg with the old references, a SYSTEM event, zero amounts, old papers as uploads): visible to staff and the buyer, refused by every write (shipment, leg, event), and their departure still counts as the factory's ship date in the on-time score. The order's next step at READY_TO_SHIP is `CHOOSE_SHIPPING` until the buyer picks freight or a hand-over (the factory can't book its pickup before); `allowedTransitions` never offers SHIPPED (`BY_DEPARTURE`). `OrdersService.transition` refuses SHIPPED for everyone (a dispute may resume an order that had left); orders move to SHIPPED only when their shipment departs (`TrackingService` → `OrdersService.advance`), which checks the balance and the shipping charge itself. GarmentGate is the shipper: partners (`LogisticsPartner`) only ever deal with GarmentGate, factories deliver to GarmentGate **hubs**, and nothing a partner, a factory or a buyer receives names the other side. Partner costs live in **rate cards** (staff only); `FreightQuotesService` asks every `ShippingRateProvider` (`MANUAL` reads the rate cards; aggregators and tracking APIs plug in through the `RATE_PROVIDERS` token), applies the most specific `LogisticsMarginRule` (`pickLogisticsMarginRule` + `applyLogisticsMargin`) and insures 110% of CIF. Freight math is integer-only (`freight.ts`: grams, litres, chargeable weight, W/M for LCL, whole containers); landed costs are estimates from the admin `DutyRate` table (longest HS prefix, CIF or FOB valuation); `consolidationSplit` shares one shipment's price by chargeable weight. Settings (`platform_settings.logistics`): shipper mode (`GARMENT_GATE_EXPORTER` / `SWITCH_BL` / `HUB_CONSOLIDATION`), insurance rate, quote validity. **Buyer shipping step** (`order-logistics.service.ts`, `/orders/:code/logistics`, buyer only): the buyer picks destination, port, incoterm (`GG_INCOTERMS`: C/D terms only; `modesFor` decides sea/air/DDP/domestic) and insurance; each mode's cheapest option is stored as a `LogisticsQuote` (price locked, valid `quoteValidityDays`; cost, partner and margin staff only) and shown through the strict `BuyerShippingOptionSchema` with a landed-cost estimate. Cargo is estimated from the quantity (`pieceWeightGrams` / `pieceVolumeMl` settings) until packing details exist. DDP is only offered when the duty can be estimated (staff set `orders.hsCode` via `PATCH /admin/logistics/orders/:code/hs-code`). Accepting (one ACCEPTED quote per order, partial unique index) sets the order's incoterm and destination; the charge is a `LOGISTICS` payment into escrow (`PaymentsService.startOrderCharge`), and `SHIPPED` is refused until it's paid. Rate cards in another currency are converted at the stored FX rate. **Own forwarder (hand-over)**: instead of GarmentGate freight the buyer can name its own forwarder (`PUT /orders/:code/logistics/handover`, `HandoverRequestSchema`): an ACCEPTED quote with mode `HANDOVER`, incoterm FCA and nothing to pay. The factory still delivers to a hub; the shipment has one `HUB_HANDOVER` leg (no partner), departing moves no money, the buyer's papers are CI/PL/CO only (`documentTypesFor(shipperMode, { mode, insured })`: no B/L for a hand-over, no insurance certificate for uninsured cargo), and one hand-over shipment serves one forwarder. The forwarder's name, contact and reference are staff only (board, shipment page) and never reach the factory. **Factory → hub → shipment** (`hub-flow.service.ts`, `consolidation.service.ts`, `shipments.service.ts`): for a managed order (one with an ACCEPTED quote; `isManaged`) the factory gives packing details (`OrderPacking`, carton dims → litres), books a pickup to an active GarmentGate hub in its country only (one live pickup per order, partial unique index) and prints `renderCartonMarkings` (hub, order, carton n/N: no buyer). Once packed, re-quotes price the packed cargo. The factory's part ends at the hub: its on-time score (`trust/performance.service.ts`) compares the first `HubReceipt` with the requested ship date. Staff schedule/collect pickups and record `HubReceipt`s (count, condition, repack/relabel, `HUB_PHOTO`s through the media worker). Buyers can ship several orders together: `ConsolidationService` prices the combined cargo, shares it by chargeable weight with `splitPriceAndCost` (price share never below cost share) and stores one OFFERED quote per order under a `Consolidation`; accepting accepts them all. Staff build a `LogisticsShipment` (code `SHP-…`) from orders received at one hub with the same buyer, mode, terms, destination and currency (a DB trigger refuses another buyer's order on a shipment; an order is on one active shipment at a time), with legs planned from mode and incoterm; leg costs replace the estimated partner cost. Documents (`logistics-documents.ts`, numbered `SHP-…-CI` etc. in `logistics_documents`) follow `documentTypesFor(shipperMode)`: the commercial invoice, certificate of origin and insurance certificate name the buyer; the B/L, packing list, label and markings consign "to order of GarmentGate"; only the staff-held original B/L of a switch names the factory. **Partners and tracking** (`partner-portal.service.ts`, `partner.controller.ts`, `tracking.service.ts`): `PARTNER` users belong to one `LogisticsPartner` (`users.logisticsPartnerId`, DB check), are invited from the admin partners tab (`POST /admin/logistics/partners/:id/users`, password set from the reset email) and are kept off every other route by the `RolesGuard` like inspectors. `/partner/legs/*` only returns the partner's own legs (strict `PartnerLegSchema`: hubs, ports, cargo and their agreed cost, GarmentGate as the customer, never buyer or factory); they accept a leg, then set references, post events and upload papers (`ShipmentUpload`, presigned with `@UploadThrottle`, sanitized by the media worker; staff only until staff publish the cleaned copy to the buyer with `PATCH /admin/logistics/shipments/:code/uploads/:id`, shown on the buyer's tracking as `papers` under neutral names `SHP-…-bill-of-lading-1.pdf`), and fetch only `PARTNER_DOCUMENTS`. Events (`recordEvent`, staff or partner) follow `canAdvanceShipment`; the public note is contact-filtered and scrubbed of factory and partner names before buyers see it. The first `IN_TRANSIT` is the **departure**: every order must be READY_TO_SHIP with its balance and logistics charge paid and every leg priced; orders move to SHIPPED and, per order, the paid logistics charge leaves escrow to `PARTNER_PAYABLE` (per partner, ledger accounts carry `logisticsPartnerId`) by its cost share with the rest to revenue (key `logistics-depart:<shipment>:<order>`). Staff then pay each leg (`POST .../legs/:id/payout`, an OUTBOUND `Payment` with `logisticsShipmentId`). Buyers follow `GET /orders/:code/logistics/tracking` (strict `BuyerTrackingSchema`: hubs shown as "GarmentGate hub") and fetch `BUYER_DOCUMENTS` once departed. **Claims and reports** (`claims.service.ts`, shared `logistics/claims.ts`, `reports.ts`; staff only under `/admin/logistics/claims` and `/reports`): staff open a `LogisticsClaim` (LOSS / DAMAGE / SHORTAGE / DELAY, code `CLM-…`) on an order that has left with GarmentGate, optionally linked to the buyer's dispute (the admin dispute view shows the shipment and links to it) and to the leg where it happened. It snapshots the insured value (110% of CIF when the buyer took insurance, else 0); one live claim per order (partial unique index). OPEN → SUBMITTED (insurer reference) → SETTLED / REJECTED. Settling posts everything in one transaction (`settlementError` and a DB check cap it): compensation to the buyer as a GarmentGate-funded REFUND (revenue → cash), recovery from the insurer as an `INSURANCE_RECOVERY` payment on the shipment (cash ← revenue, never above the insured value) and a chargeback against the leg's partner (partner payable → revenue, never above the leg's cost). Buyers see the claim and compensation on the tracking card (`BuyerClaimSchema`), partners their chargeback (`PartnerClaimSchema`), the factory nothing. `logisticsRevenue` reports per currency (never mixed): revenue of shipments departed in the period, partner cost, insurance premiums, net claims and margin, by month and mode, plus partner costs, payouts and chargebacks. **Anonymity**: the last test in `logistics-tracking.e2e-spec.ts` fetches everything buyer, factory and partners can (JSON, notifications, every PDF) and asserts no other side's names, codes or the hub address leak; partner documents carry only the `SHP-…` code (packing lists number lots, not orders). Extend it with every new logistics response. The Playwright journey 5 runs order → pickup → hub receipt → shipment → departure → partner delivery → buyer confirmation on the seeded `ORD-2026-00018` (`prisma/seed/logistics.ts`: hub `HUB-BD-01`, Bayline Cargo with portal login `ops@baylinecargo.example`, Ashulia Road Haulage, an air rate card).
- **Supply contracts and merchandisers** (`modules/contracts`, shared `order/contracts.ts`; pages `/buyer/contracts`, `/manufacturer/contracts`, `/admin/contracts`): staff agree a frame agreement (`POST /admin/contracts`, code `CTR-…`: verified buyer and factory by code, one product, buyer and factory price per piece (buyer ≥ factory), contracted volume, minimum call-off, deposit, incoterm, lead time, period; DB check keeps it sane). The buyer sees its price and the factory's `MFR-` code (strict `BuyerContractSchema`), the factory its price and the `BYR-` code (`ManufacturerContractSchema`); title and specification are scrubbed of the other side's names. A **call-off** (`POST /contracts/:code/call-offs`, `callOffError`: active, in the period, ≥ the minimum, within the volume) claims the volume with one conditional update (two at once never overdraw it) and creates an order at the contract prices (`orders.contractId`), advanced straight to DEPOSIT_PENDING so releases and the deposit work as for any order. Each buyer account can have a **merchandiser** (`companies.merchandiserId`, an active staff user; `PUT /admin/buyers/:code/merchandiser`, picked on the admin order page): the buyer sees their name (`GET /buyer/merchandiser`), and call-offs notify them first (staff otherwise).
- **Exception flow** (`modules/exceptions`, shared `order/exceptions.ts`, staff page `/admin/exceptions`): `lateness` measures how far an order being made (IN_PRODUCTION / QC / READY_TO_SHIP) is behind plan: the oldest unfinished production stage past its `plannedAt`, or the requested ship date passing before the goods reach a hub. `GET /admin/exceptions` lists orders 7+ days late, failed final inspections and rejected samples. The BullMQ `order-exceptions` sweep (hourly; not scheduled in tests, call `ExceptionsService.sweep`) alerts staff, the factory and the buyer once a week per late order (`orders.delayAlertedAt`, claimed by a conditional update). **Factory replacement** (`POST /admin/orders/:code/replace-factory`, `ReplaceFactorySchema`: a verified factory's code, its price per piece ≤ the buyer's, a reason) works until the goods reach a hub: the order moves to the new factory at the same buyer price (commission recomputed at the order's rate); the old factory's releases are **superseded** (`order_releases.supersededAt`; one live release per trigger is a partial unique index): released ones stay its own (payouts still run), the rest are cancelled; new releases are worked out on the new price with the material advance DUE at once, and GarmentGate funds what the old factory already received back into escrow (revenue → escrow, `OrderFactoryChange.fundedMinor`) so the books stay whole. Production starts over (`OrdersService.replanProduction`), old pickups and packing are dropped, the old factory loses access and the buyer sees the new `MFR-` code. Factory payout views only show live releases.
- **KPIs and unit economics** (`modules/kpis`, shared `kpi/kpi.ts`, staff page `/admin/kpis`): the business plan's Phase 1 scoreboard for a period (`GET /admin/kpis?from&to`). Per order confirmed in the period, `orderContribution` = margin + commission + shipping margin (paid `LOGISTICS` charge less the shipment's cost share, or the quoted cost) + fee margins, less payment/FX fees, merchandising time and the claims reserve; the assumptions are `platform_settings.unit_economics` (`PUT /admin/kpis/settings`, defaults 2.5% / USD 100 / 1% / USD 20,000 fixed a month). Platform totals are USD at reference rates (an order without a rate counts 0). Operational KPIs: on time = at the hub (or, historically, shipped) by the requested ship date; first pass = an order's first final inspection; repeat buyer = ordered again within 6 months; quote → order; active verified factories (an order in 90 days); capacity booked; claim rate (dispute or logistics claim on orders delivered in the period); inspector assignment hours (`inspections.assignedAt`). `gates()` tracks the roadmap: gate 1 = 50 paid orders (deposit paid, all time) and 85% on time; gate 2 = every order positive and 30% repeat buyers; gate 3 = last 30 days' contribution ≥ monthly fixed costs and a working-capital line staff tick in the settings. `kpi.test.ts` reproduces the plan's 1,000-polo example (≈ USD 680).
- **Search** (`modules/search`): Meilisearch documents are built from `toPublicProduct` / `toPublicManufacturer` plus an explicit key allowlist (`search-documents.ts`), so the index holds nothing a buyer couldn't see. Only published products from listed, verified factories are indexed. Services call `SearchService.syncProduct` / `syncManufacturer` after any change that affects visibility (product CRUD, profile, certificates, KYC decisions); a BullMQ `search` worker applies it. The API rebuilds the indexes on boot, and `pnpm db:seed` does the same. `MEILISEARCH_INDEX_PREFIX` keeps e2e tests (`test_`) away from the dev indexes.

## Tech stack

Turborepo + pnpm workspaces monorepo.

```
apps/
  web/        Next.js (App Router), TypeScript, Tailwind CSS, shadcn/ui, Motion,
              TanStack Query, React Hook Form + Zod, next-intl
  api/        NestJS, Prisma, PostgreSQL, Redis, BullMQ, Socket.io,
              Meilisearch, S3-compatible object storage
packages/
  shared/     Zod schemas + inferred TypeScript types used by both web and api
  config/     Shared ESLint (base/nest/next), tsconfig (base/library/nestjs/nextjs) and Prettier configs
  emails/     React Email templates + renderEmail(); preview with `pnpm --filter @garmentgate/emails preview`
```

Current versions: Node 22 LTS, pnpm 12, Turborepo 2, Next.js 16 (Turbopack, React 19), NestJS 12 (ESM), Tailwind 4, shadcn/ui (base-nova style, Base UI primitives), Zod 4, Vitest 5.

- **TypeScript is pinned to 6.0.x** and **ESLint to 9.x**: typescript-eslint, @nestjs/swagger and the React/a11y ESLint plugins don't support TS 7 / ESLint 10 yet. Don't bump them until those peer ranges allow it.
- **Dev and build outputs are separate**: `pnpm dev` compiles the API to `apps/api/dist-dev` (`tsconfig.dev.json`) and Next keeps its dev build under `.next/dev`, so `pnpm build` (which empties `apps/api/dist`) can run while dev is running.
- **apps/api is native ESM** (`"type": "module"`, `NodeNext`): relative imports need the `.js` extension (`import { X } from './x.js'`).
- **packages/shared is compiled** with `tsc` to `dist/` and consumed via its `exports`. Turbo builds it before any dependent task, and `pnpm dev` runs it in watch mode.
- **Env vars are validated at boot**: the API's schema lives in `apps/api/src/config/env.schema.ts` and is passed to `ConfigModule` as a Standard Schema. Add new variables there and to `.env.example` together. Read them with `ConfigService<Env, true>` / `AppConfigService` and `{ infer: true }`, never `process.env` (sole exception: `src/instrument.ts`, which runs before Nest). Optional settings use `unsetIfEmpty` so a copied `KEY=` counts as unset. In production `ProductionEnvSchema` refuses placeholder secrets, HTTP origins, insecure cookies, a missing email key, or Stripe without its webhook secret: extend it with every new secret.
- **Swagger** reads Zod schemas directly: `@ApiOkResponse({ standardSchema: SomeSchema })`.
- **Rate limiting**: `HttpThrottlerGuard` is global and runs **after** the auth guards (registered in `AuthModule`), counting signed-in requests per user and anonymous ones per IP. Opt out with `@SkipThrottle()` (health checks only). Tighter limits: `@Throttle` on auth routes, and `UploadThrottle` / `MessageThrottle` / `ThreadThrottle` from `common/throttle/limits.ts`: **every new presigned-upload endpoint gets `@UploadThrottle()`**.
- **CSRF**: on top of `SameSite=Lax` cookies, `originCheckMiddleware` (`common/security/origin-check.ts`) refuses state-changing requests from origins outside `CORS_ORIGINS` or marked `Sec-Fetch-Site: cross-site`. Only the signed Stripe webhook is exempt; add any other machine-to-machine endpoint there deliberately.
- **Uploads**: `FilesService.confirmUpload` (every attach goes through it) checks size and type, the file's **magic bytes** (`file-signature.ts`; add a signature when accepting a new MIME type) and, with `CLAMAV_HOST` set, scans it with ClamAV (`malware-scanner.ts`). Infected → deleted, `scanStatus = INFECTED`; scanner down → the request fails, never a pass. `PENDING` means not scanned.
- **Error monitoring**: Sentry on both apps (`apps/api/src/instrument.ts` imported first in `main.ts`, `SentryGlobalFilter`; web `instrumentation.ts` / `instrumentation-client.ts`, error boundaries). No-op without a DSN. Never send identities: `dataCollection` collects nothing personal and `scrubEvent` strips cookies, headers, bodies, query strings and all user fields but the id; no Session Replay. BullMQ workers extend `MonitoredWorker` so jobs that fail their last retry are reported.
- **pnpm only runs dependency install scripts listed in `allowBuilds`** in `pnpm-workspace.yaml`. Review any new entry before allowing it.
- **Prisma 7** (`apps/api/prisma/schema.prisma`, config in `apps/api/prisma.config.ts`) generates an ESM client into `apps/api/src/generated/prisma` (git-ignored, regenerated on install/build). Import from `../generated/prisma/client.js`. Rules Prisma can't express live as hand-written SQL in the first migration: positive amounts, buyer price ≥ manufacturer price, **ledger transactions must balance (checked at commit) and are append-only**, and **a buyer and a manufacturer can never be in the same conversation**. Keep them when you add migrations.
- **BullMQ 6** needs an `ioredis` client instance (see `src/common/queue/queue.module.ts`); passing connection options under ESM makes it loop and run out of memory.

### Auth and routing

- The browser only ever calls same-origin `/api/*`; `apps/web/next.config.ts` rewrites it to the API. Auth lives in **httpOnly, SameSite=Lax cookies**: `gg_at` (15-min JWT access token: `sub`, `role`, `ev` email-verified, `kyc` status) and `gg_rt` (30-day opaque refresh token, stored hashed, **rotated on every use**; replaying a rotated token outside a 30 s grace window revokes the whole session family).
- API: `JwtAuthGuard` and `RolesGuard` are global. Every route requires a signed-in user unless marked `@Public()`; restrict with `@Roles('ADMIN')`; read the user with `@CurrentUser()`. Validate bodies with `new ZodValidationPipe(SharedSchema)`.
- Web: `apps/web/src/proxy.ts` (Next 16's replacement for `middleware.ts`) decides which page each user sees using `homePathFor()` from `packages/shared`: admins → `/admin`; buyers/manufacturers → `/onboarding` until submitted, `/pending` while under review, then `/buyer` or `/manufacturer`. It refreshes expired sessions server-side. It only decodes the JWT for routing; the API is the security boundary.
- After anything that changes claims (onboarding submit, KYC decision, email verification) call `POST /api/auth/refresh` (`refreshUser()` on the web) so routing picks it up.
- KYC files go **browser → MinIO/S3 directly** via presigned POST (`POST /kyc/uploads`), then are attached with `POST /kyc/documents` or `/kyc/certifications`; the API checks the object exists with the declared type and size. Downloads are 5-minute presigned GETs for the owning company or admins only.
- Emails are queued (BullMQ) and rendered from `packages/emails`. **Without `RESEND_API_KEY` they are logged to the API console instead of sent**: copy verification and reset links from there in development.

- **apps/web**: server components by default; client components only where interactivity is needed. Server state goes through TanStack Query; forms use React Hook Form with `zodResolver` and the schema from `packages/shared`. All user-facing strings go through next-intl; no hard-coded copy. UI primitives come from shadcn/ui; animations use Motion and respect `prefers-reduced-motion`.
- **apps/api**: NestJS modules per feature. Prisma is the only DB access layer. Long-running or retryable work (emails, media processing, search indexing, payouts) runs as BullMQ jobs. Real-time chat and notifications go over Socket.io, which needs the same auth and contact filtering as HTTP. Meilisearch indexes contain only anonymized, buyer-safe fields. Files go to S3-compatible storage through signed URLs; never serve them from a public bucket.
- **packages/shared**: the single source of truth for request/response shapes, enums (roles, order statuses, currencies), and constants. Types are inferred from Zod (`z.infer`); don't hand-write duplicate interfaces.
- **Local infrastructure** (Postgres, Redis, Meilisearch, MinIO for S3) runs in Docker via `docker compose`.

## Coding conventions

- **Strict TypeScript everywhere** (`"strict": true`, `noUncheckedIndexedAccess`). No `any`: use `unknown` and narrow, or write a proper type. Don't silence the compiler with `as` casts or `@ts-ignore`; `@ts-expect-error` needs a comment explaining why.
- **Feature-based folders.** Group by domain, not by technical layer:
  - api: `apps/api/src/modules/<feature>/` (controller, service, module, serializers, tests)
  - web: `apps/web/src/features/<feature>/` (components, hooks, queries, forms), with routes in `app/`
  - shared: `packages/shared/src/<feature>/`
- **DTOs are validated with shared Zod schemas.** Every request body, query and params object, and every socket payload, is parsed with a schema from `packages/shared` via a Zod validation pipe. The web app uses the same schema for its forms. Change the schema once, in `shared`.
- **Money is integer minor units plus a currency code.** Store `amountMinor: Int` (or `BigInt` where totals can be large) next to `currency` (ISO 4217, e.g. `USD`). Never use floats or decimals for money in code or JSON. Do the arithmetic in minor units, and format for display only at the edge with `Intl.NumberFormat`, taking the currency's minor-unit exponent into account (JPY has 0, USD has 2, etc.).
- Dates are stored in UTC and sent as ISO 8601 strings.
- IDs exposed outside the platform are opaque (cuid/uuid or public codes), never sequential database IDs.
- Prefer small, pure, testable functions. Business rules (pricing, margins, contact filtering, status transitions) live in services with unit tests, not in controllers or components.
- Write tests with the feature: unit tests for services and the contact filter, e2e tests for API routes (including "a buyer cannot see manufacturer identity" checks), and component tests for non-trivial UI. `test/security.e2e-spec.ts` must keep passing: a new non-public route is checked for anonymous access automatically (from the OpenAPI document), but add new order/RFQ/thread-scoped routes to its cross-tenant probes, with valid bodies.

## UX principles

- **Simple journeys.** Each role has a few primary flows (buyer: discover → RFQ → compare quotes → order → track; manufacturer: profile → respond to RFQ → fulfil order). Design these first and keep them linear.
- **Max 3 clicks to any key action** from the role's dashboard (create RFQ, reply to a quote, open a chat, view order status).
- **Mobile-first.** Build for small screens first, then enhance for larger ones. Touch targets are at least 44px, and nothing scrolls horizontally on the page body.
- **Every list and data view has loading, empty and error states.** Loading uses skeletons, empty states explain what to do next and include the primary action, and error states say what went wrong and offer a retry.
- Accessible by default: semantic HTML, labelled form fields, keyboard navigable, WCAG AA contrast.
- All copy goes through next-intl; layouts must survive longer translations and RTL where supported.
- **Languages**: `en.json` is the source; `bn/es/fr/ar.json` fall back to English key by key (`messages/README.md`). Locales are registered in `packages/shared/src/i18n/locales.ts`; only `enabled` ones are routable in production (all in development, to check layouts). Every route lives under `app/[locale]/`, but URLs carry no prefix: the proxy runs next-intl with `localePrefix: 'never'`, reading the `gg_locale` cookie the API sets from the user's preference (login and `PATCH /auth/me/preferences`). Use logical CSS (`ms-*`, `pe-*`, `start-*`, `text-start`) so Arabic flips; `<html dir>` comes from the locale. Don't call `useSearchParams` in a page's main content just to read a hint: it makes the page client-rendered (use `useClientSearchParam`).
- **Money display**: show amounts with `useMoney()` (`@/lib/use-money`): the exact amount in the order's currency, plus "≈" in the user's display currency (reference rates from `GET /fx/rates`). Inputs and staff views stay exact (`formatMoney`).
- **Images** from uploads render with `<Rendition urls sizes>` (srcset over the 320/800/1600 WebP renditions, lazy unless `priority`).

## Design system

Browse everything at **http://localhost:3000/dev/ui** (dev only; 404 in production). Aim: calm, precise, trustworthy B2B (Linear/Stripe), not an admin template.

- **Tokens** live in `apps/web/src/app/globals.css` with full light and dark values. Use semantic classes only (`bg-card`, `bg-surface`, `text-muted-foreground`, `text-subtle-foreground`, `border-border-strong`, `bg-primary-soft text-primary-ink`), never raw palette colours or hex. Brand: deep "loom" teal (`primary`), `brand-deep` for dark marketing panels and `brand-gold` as a sparing accent.
- **Status tones**: `success`, `warning`, `info`, `progress`, `danger`, `neutral`, each with `-soft` (background) and `-ink` (text). **Always show a status with `<StatusBadge domain="order" status={…} />`**. Tones come from `STATUS_TONES` in `packages/shared/src/status/statuses.ts`, labels from `statuses.<domain>.<STATUS>` in messages. Add new statuses to both.
- **Type**: Instrument Sans for UI, **Instrument Serif (`font-display`, `text-display*`) only for marketing headlines**, Geist Mono for codes (`MFR-BD-0421`, order numbers; use `<Badge variant="code">`). Numbers in tables and stats use `tabular`. Money is formatted with `formatMoney(minor, currency, locale)` from `@/lib/format`.
- **Elevation**: `shadow-xs` on resting surfaces, `shadow-md` on hover, `shadow-lg/xl` for popovers and dialogs. Radius base is 10px (`rounded-lg`); cards use `rounded-xl`.
- **Components** in `src/components/ui` are shadcn (Base UI) restyled to these tokens. Buttons and inputs are 44px on mobile, compact from `md`. A Button with `render={<Link …/>}` keeps link semantics automatically. Dialogs become bottom sheets on mobile.
- **Patterns** in `src/components/patterns`: `PageHeader`, `EmptyState`, `ErrorState`, `StatCard`, `StatusBadge`, `FileDropzone`, `Timeline`, `PageTransition`, `Appear`, `DataTable` (TanStack Table v9: search, filters, sorting, pagination, CSV export: use it for every admin list), `Rendition`. Entrance animations never start server-rendered content at `opacity: 0` (it delays LCP): `PageTransition`/`Appear` only animate after hydration. Every list uses skeleton → `EmptyState` (with the next action) / `ErrorState` (with retry).
- **Buyer discovery** (`src/features/discovery`): `/buyer/search` (instant search, facets, sort, grid/list), `/buyer/products/[id]`, `/buyer/factories[/code]`, `/buyer/shortlists` and the dashboard. Search state lives in the URL via **nuqs** (`search-params.ts`; `NuqsAdapter` is in `providers.tsx`), so pages using it render inside `<Suspense>`. "Request quote" / "Order sample" call `POST /catalog/products/:id/request`, which creates an RFQ (plus a CATALOG sample) invited to that factory only. Favourites are the company's default "Favorites" shortlist; heart buttons read `/shortlists/saved` and update optimistically.
- **App shell** (`src/features/shell`): each role's `layout.tsx` wraps pages in `<AppShell role=…>` (collapsible sidebar, mobile bottom nav with "More" sheet, ⌘K command menu, notifications bell, profile menu with theme switch). Navigation is defined once in `nav.ts`; sections not built yet render a "Coming soon" page from `[section]/page.tsx`. When you build a section, add its own route folder and it takes precedence.
- **Motion**: use Motion with the `ease-out-expo` curve, short durations (150–300 ms for UI, ≤ 600 ms for marketing reveals). `MotionConfig reducedMotion="user"` and a global CSS rule disable motion for users who ask.
- **Cache Components gotchas**: read `params`/`searchParams` inside `<Suspense>`; no `new Date()` in prerendered server output (use a `'use cache'` function); use `useSyncExternalStore` (see `@/lib/client-hooks`) instead of setting state in an effect for client-only values.


### Day to day

```bash
pnpm dev                     # shared (watch) + api :4000 + web :3000 together
pnpm dev --filter web        # one app only (web | api); shared is built first

pnpm db:up                   # start Postgres, Redis, Meilisearch, MinIO (+ bucket) and wait until healthy
pnpm db:down                 # stop the containers (data is kept)
pnpm db:reset                # DELETE all local data volumes, recreate, migrate and seed
pnpm db:logs                 # follow container logs

pnpm db:migrate              # create + apply a migration after editing schema.prisma (prisma migrate dev)
pnpm db:deploy               # apply pending migrations (CI / production)
pnpm db:generate             # regenerate the Prisma client
pnpm db:seed                 # WIPE app tables and load demo data (logins printed at the end)
pnpm db:studio               # browse the database in Prisma Studio

pnpm build                   # build all packages and apps
pnpm start                   # run the production builds
pnpm lint                    # ESLint (type-aware) everywhere
pnpm typecheck               # tsc --noEmit everywhere
pnpm test                    # unit tests (Vitest)
pnpm test:e2e                # API e2e tests against real Postgres/Redis/MinIO (needs `pnpm db:up`);
                             # uses its own `garmentgate_test` database, reset on every run
pnpm format                  # Prettier write; `pnpm format:check` to verify
pnpm --filter web test:journeys  # Playwright: the 5 main journeys (stop `pnpm dev`; build first;
                             # own `garmentgate_e2e` database, reseeded each run)
```

### Production

- Deployment guide: `docs/deployment.md` (Vercel web; API as the `apps/api/Dockerfile` image on Railway/Render/Fly.io or a VPS; managed Postgres/Redis; R2; Meilisearch Cloud; ClamAV; Sentry). Security review: `docs/security.md`. Overview and setup: `README.md`.
- Images: `docker build -f apps/api/Dockerfile .` (`--target migrate` for `prisma migrate deploy`) and `docker build -f apps/web/Dockerfile --build-arg API_URL=… .` (standalone output; `API_URL` is baked into the rewrite at build time).
- First admin in a new environment: `node scripts/create-admin.mjs <email>` in `apps/api` (or the API image), password prompted.
- CI: `.github/workflows/ci.yml` runs audit (high+), format, lint, typecheck, unit tests, build, API e2e, the Playwright journeys and both image builds.

Before finishing any change, run `pnpm lint`, `pnpm typecheck` and `pnpm test`.
